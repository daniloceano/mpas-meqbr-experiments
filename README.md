# mpas-meqbr-experiments

Analysis of the MPAS-Atmosphere experiment set over the **Brazilian equatorial
margin** at ~5 km (`meqbr_05km`), run to answer two practical questions:

1. **Which configuration should carry the climatological runs?**
2. **Do these runs add enough skill over ERA5 to serve as an alternative for
   offshore wind resource assessment on this coast?**

The simulations live elsewhere and are read in place, never copied:
`/p1-swell/danilocs/MPAS-Research/runs/meqbr_05km` — see its `EXPERIMENTS.md`
for what each experiment *is*. This repository holds only the analysis.

> **Read this first.** The SST forcing in `EXP01` and `EXP02` carries the NOAA
> OISST **land fill value (273.15 K) into coastal ocean cells**, and both LiDAR
> validation sites sit inside the affected strip (P0: 291.5 K instead of
> ~300 K). Their comparison against `CTL` therefore measures an interpolation
> error, not the SST-update or boundary-treatment hypotheses those experiments
> were designed to test. Details, evidence and what to do about it:
> [`SCIENTIFIC_NOTES.md`](SCIENTIFIC_NOTES.md), Result 1. The check is automated
> and fails loudly: `scripts/03_selection/check_sst_forcing.py`.

## What is being compared

| | `CTL` | `EXP01` | `EXP02` |
|---|---|---|---|
| Delta vs parent | baseline | daily NOAA OISST SST update | buffered mesh (5 → 32 km ramp) + wider ERA5 box |
| Mesh | `meqbr_05km` (76 813 cells) | same | `meqbr_05km_buf` (95 138 cells) |
| Relative cost | 1.00 | 1.00 | 1.24 |
| Status | complete | complete | running; see generated `docs/run_status.md` |

Two 41-day integrations each (10-day spin-up discarded), each carrying a
different in-situ instrument: **2021 → P0 floating LiDAR**, **2022 → LPI fixed
LiDAR**. Current disk status: [`docs/run_status.md`](docs/run_status.md)
(regenerated by the inventory script, not edited).

The design is **cumulative**: `EXP02 = EXP01 + boundary treatment`, so
`EXP02 − EXP01` is the *incremental* effect of the boundary treatment given the
SST update is already on.

## Data sources

| Dataset | Role | Resolution / period | Access |
|---|---|---|---|

INMET's own API is not reachable from this host, so the Brazilian automatic
stations are taken from NOAA's ISD archive instead — see
[`docs/data_sources.md`](docs/data_sources.md).

## Workflow

Numbered stages; each is re-runnable and the expensive ones are incremental, so
re-running after a simulation finishes only reads the new hours.

```
00_setup/       what exists on disk, and is it what config says
01_extract/     site time series, domain field statistics, ERA5, stations   <- the heavy pass
02_validation/  metrics and figures at the LiDAR sites
03_selection/   ranking with uncertainty, mechanism checks, SST audit
04_era5/        added value, climatological context, resource maps
05_exploration/ maps, difference maps, cross-sections, animations
06_report/      portable HTML report from consolidated tables and media
```

```bash
conda env create -f environment.yml && conda activate mpas-meqbr
cp config/paths.example.yaml config/paths.local.yaml   # edit for your machine
python scripts/00_setup/link_observations.py           # once
./scripts/run_all.sh                                   # everything, in order
./scripts/run_all.sh 02                                # or from a stage onward
```

Every script takes `--help`, and most take `--experiments`, `--period` and
`--common-period/--no-common-period`.

**When `EXP02` finishes**, re-run from stage 00: the extraction picks up only the
new hours, and every comparison window widens automatically.

## Repository layout

```
config/         experiments.yaml (what each run is), sites.yaml (validation sites
                and pairing rules), paths.example.yaml -> paths.local.yaml (gitignored)
src/mpas_meqbr/ config, io, mesh, vertical, obs, era5, pairing, metrics, fields, plotting
scripts/        the numbered pipeline above, plus run_all.sh
data/           obs/ (LiDAR symlinks), era5/, stations/, metadata/ (provenance JSON)
results/        tables/ (versioned - the record of what was decided),
                site_timeseries/, fields/, logs/ (regenerable, gitignored)
figures/        validation/, selection/, era5/, exploration/, animations/ (gitignored)
results/report/ portable generated HTML bundle and provenance manifest
docs/           data_sources, validation_protocol, analysis_conventions, run_status
notebooks/      scratch exploration only
```

`results/tables/` is version controlled on purpose: it is small, and it is the
record of what was decided and when. Everything else under `results/` and all of
`figures/` regenerates from the scripts.

## Conventions worth knowing before editing anything

Full list in [`docs/analysis_conventions.md`](docs/analysis_conventions.md). The
three that cause the most damage when ignored:

- **Never assume the file list equals the analysis window.** `EXP02`'s history
  still contains its spin-up. Always go through `io.select_window()`.
- **Nearest-cell indices are per leg.** The two meshes do not share cell indices.
- **Compare experiments over the same hours.** `pairing.load_paired(...,
  common=True)` and `fields.assert_same_window()` enforce it; a difference
  between different windows is a difference in weather.

## Reproducibility

- Machine paths live only in `config/paths.local.yaml` (gitignored); the
  scientific metadata in `config/*.yaml` is version controlled.
- Every figure carries a footer naming the script that made it, the averaging
  window and the processing choices that matter.
- Every download writes a provenance JSON with the request, the checksum and the
  date.
- Raw simulation output, ERA5 downloads and observation exports are never
  committed.
